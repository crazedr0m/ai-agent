# ТЕХНИЧЕСКОЕ ЗАДАНИЕ (АРХИТЕКТУРНЫЙ КОНЦЕПТ)
## Мультиагентный модуль оркестрации разработки с динамическим наймом и адаптивной логикой переходов (MAM-Dev Platform)

---

### 1. Назначение и цель системы
**MAM-Dev Platform** — это программная среда оркестрации, управляющая распределенной командой специализированных ИИ-субагентов. Цель системы — автоматизация полного цикла разработки программного обеспечения (SDLC) от первичного сбора требований до развертывания готового продукта. Система использует декларативное управление процессами, перекрестную критику, динамический найм ролей под стек проекта и каскадную эскалацию ошибок на верхние уровни иерархии.

---

### 2. Ключевые архитектурные слои
Система изолирует логику рассуждений от непосредственного выполнения действий и состоит из четырех взаимосвязанных слоев:

*   **Слой состояния (Global State / Память):** Единое централизованное хранилище данных проекта (Single Source of Truth), доступное оркестратору для контроля, а агентам — для чтения и записи артефактов.
*   **Слой оркестрации (Dynamic State Machine / Адаптивный граф):** Программный контроллер, вычисляющий маршруты переходов между этапами, управляющий петлями критики и каскадными откатами (эскалацией).
*   **Слой агентов (Пул ролей / Registry):** Реестр системных инструкций (System Prompts), инициализируемых под конкретные задачи.
*   **Слой навыков (Инструменты действия / Tools API):** Программные интерфейсы (модули нативных функций), через которые агенты физически взаимодействуют с операционной системой, диском, сетью и пользователем.

---

### 3. Спецификация Глобального Состояния (Global State Schema)
Объект состояния передается между узлами графа и содержит следующие ключевые структуры:

*   `project_metadata`: 
    *   `project_id`: Уникальный идентификатор сессии.
    *   `technology_stack`: Список определенных технологий (например, `["React", "FastAPI", "PostgreSQL", "Docker"]`).
    *   `required_capabilities`: Динамический список навыков, необходимых для выполнения проекта.
*   `workflow_context`:
    *   `current_stage`: Текущий активный узел (например, `CODE_REVIEW`).
    *   `execution_history`: Хронологическая цепочка пройденных узлов.
    *   `loop_counters`: Счетчики итераций для локальных петель критики (сброс при переходе на новый этап).
*   `artifacts_repository`:
    *   `requirements_doc`: Финальное или промежуточное ТЗ.
    *   `architecture_blueprint`: Описание сущностей, API и схем БД.
    *   `source_code`: Словарь структуры файлов проекта и их содержимого.
    *   `test_suites`: Набор автотестов.
    *   `deployment_manifests`: Конфигурации среды (Dockerfile, CI/CD).
*   `incident_management`:
    *   `critique_logs`: Замечания критиков и ревьюеров.
    *   `escalation_stack`: Стек откатов, содержащий причину (`reason`), узел-отправитель (`source_stage`) и целевой узел (`target_stage`).

### 4. Расширенная Ролевая Модель Субагентов
Каждый субагент представляет собой инстанс большой языковой модели (LLM), ограниченный жестким системным промтом, определяющим зону ответственности, правила мышления и метрики успешности работы.

1.  **Агент-Менеджер (Бизнес-аналитик):**
    *   *Цель:* Превратить неопределенный запрос пользователя в исчерпывающее техническое задание.
    *   *Поведение:* Агрессивно ищет двусмысленности в ответах человека, сопоставляет требования с внутренним чек-листом полноты данных.
2.  **Агент-Архитектор (Системный дизайнер):**
    *   *Цель:* Трансляция требований в техническую структуру.
    *   *Поведение:* Проектирует связи между таблицами, структуры эндпоинтов, выбирает оптимальные паттерны интеграции.
3.  **Агент-Критик Архитектуры (Безопасность и Нагрузка):**
    *   *Цель:* Деструктивный аудит системного дизайна до начала написания кода.
    *   *Поведение:* Действует как "адвокат дьявола". Ищет потенциальные уязвимости, проблемы с горизонтальным масштабированием, узкие места и нарушения ТЗ.
4.  **Агент-Разработчик (Имплементатор):**
    *   *Цель:* Создание исходного кода строго по архитектурным лекалам.
    *   *Поведение:* Пишет чистый код, декомпозирует функции, вносит изменения точечно (через патчи), минимизирует избыточность.
5.  **Агент-UI/UX Критик (Фронтенд-контролер):**
    *   *Цель:* Верификация интерфейсных решений и пользовательских сценариев.
    *   *Поведение:* Анализирует верстку, проверяет контрастность, доступность, корректность структуры компонентов и логику переходов на экранах.
6.  **Агент Код-Ревьюер (Архивариус и Стилист):**
    *   *Цель:* Статический анализ кода на безопасность и качество до этапа компиляции.
    *   *Поведение:* Ищет "запах кода" (code smells), хардкод секретов, незащищенные SQL-запросы, проверяет следование стайл-гайдам.
7.  **Агент-Тестировщик (Инженер качества / QA):**
    *   *Цель:* Покрытие кода тестами и верификация логики работы.
    *   *Поведение:* Самостоятельно пишет юнит- и интеграционные тесты, запускает их в изолированной среде, сопоставляет логи ошибок с требованиями из ТЗ.
8.  **Агент-DevOps (Инженер инфраструктуры):**
    *   *Цель:* Упаковка приложения и обеспечение его бесперебойного развертывания.
    *   *Поведение:* Настраивает конфигурации контейнеров, проверяет сетевые доступы, порты, описывает автоматические сценарии сборки.

### 5. Динамический Наем (Dynamic Staffing) и Перестраиваемый Граф (Dynamic Routing)

Система отказывается от статичного конвейера в пользу адаптивной сборки команды и маршрута под метаданные текущего проекта.

#### Механизм динамического найма (Registry Pattern):
Оркестратор содержит реестр шаблонов агентов. Инициализация команды происходит в рантайме:
1. Этап `REQUIREMENTS` завершается. Агент-Менеджер формирует массив `required_capabilities: ["web_frontend", "relational_db", "docker_deployment"]`.
2. Оркестратор анализирует массив и активирует из реестра промты для: `Архитектора`, `Критика Архитектуры`, `Разработчика`, `UI/UX Критика`, `Код-Ревьюера`, `Тестировщика` и `DevOps`.
3. Если бы в требованиях отсутствовал пункт `web_frontend`, промт `UI/UX Критика` не загружался бы в оперативную память системы, экономя вычислительные ресурсы.

#### Декларативное управление маршрутом (Workflow Schema):
Маршрут движения по этапам описывается в виде графа зависимостей (JSON/YAML конфигурация), который может мутировать в процессе выполнения:
*   **Правило транзита:** Переход к следующему узлу возможен только при наличии флага `APPROVED` от валидирующего субагента текущего узла.
*   **Мутация на лету (Runtime Mutation):** Если на этапе кодинга Разработчик понимает, что для кэширования необходим Redis, он добавляет требование `key_value_store` в стейт. Оркестратор мгновенно перестраивает граф, врезая перед этапом тестирования дополнительную задачу для DevOps по конфигурации Redis-контейнера.

### 6. Контуры Обратной Связи и Механизм Эскалации (Escalation Engine)

Взаимодействие агентов строго регламентировано двумя типами обратной связи.

#### А. Локальная петля критики (Внутренний коммит-митинг)
Применяется для изоляции микро-ошибок внутри одного этапа без привлечения всей команды и пользователя.
*   *Пример (Архитектура):* Архитектор отправляет `architecture_blueprint` Критику. Критик находит баг ➔ Статус `REJECTED` ➔ Документ возвращается Архитектору с логом правок.
*   *Предохранитель (Circuit Breaker):* Максимальное число внутренних циклов — **3**. Если по истечении 3 итераций Критик не ставит `APPROVED`, локальный цикл разрывается и инициируется процедура эскалации на уровень выше.

#### Б. Каскадная эскалация (Уровневый откат назад)
Применяется, когда текущий уровень зашел в тупик из-за системной ошибки, допущенной на предыдущих этапах.
*   **Сценарий «Тестирование ➔ Разработка»:** Тест пал из-за опечатки в функции. Тестировщик формирует краткий отчет об ошибке, оркестратор меняет `current_stage = DEVELOPMENT`, вызывается Разработчик для исправления кода.
*   **Сценарий «Разработка ➔ Архитектура»:** Разработчик видит, что Архитектор спроектировал связь "один к одному" там, где по коду требуется "один ко многим". Разработчик вызывает системный инструмент эскалации. Оркестратор откатывает состояние на уровень `ARCHITECTURE`, пробуждая Архитектора и Критика для перепроектирования схемы.
*   **Сценарий «Архитектура ➔ Требования»:** Архитектор и Критик понимают, что технические ограничения стека (выбранного пользователем) физически не позволяют реализовать требуемую скорость обработки транзакций. Происходит эскалация на уровень `REQUIREMENTS`. Включается Менеджер, который формулирует дилемму для конечного пользователя.

### 7. Слой Навыков и Инструментов (Tools API)
Агенты не имеют прямого доступа к функциям операционной системы. Они отправляют структурированный запрос на вызов инструмента, который исполняется базовой платформой.

*   `ask_user(prompt_text)`: Доступен только Менеджеру. Выводит сообщение на экран пользователя и переводит систему в режим ожидания (блокирующий ввод).
*   `read_artifact(path)` / `write_artifact(path, content)`: Доступен всем ролям. Позволяет читать и перезаписывать файлы в рамках песочницы проекта. Системный валидатор блокирует попытки выхода за пределы рабочей директории (защита от Path Traversal).
*   `patch_file(path, search_block, replace_block)`: Доступен Разработчику и DevOps. Позволяет точечно менять строки кода, исключая необходимость гонять через контекст LLM многотысячные файлы целиком.
*   `execute_sandbox_command(cmd)`: Доступен Разработчику, Тестировщику, DevOps. Запускает bash-команды. Выполнение происходит строго внутри изолированного Docker-контейнера с ограничением по времени (Timeout = 60s) и отключенным доступом к критической инфраструктуре хоста.

### 8. Слой Сквозного Логирования и Анализа (Observability Layer)
Система разделяет телеметрию на два изолированных потока данных:

#### Поток А: Инженерный аудит (Human-Readable Business Log)
Лог на естественном языке, предназначенный для понимания человеком хода мыслей ИИ-команды.
*   *Формат:* `[ВРЕМЯ][ТИП_СОБЫТИЯ][ИНИЦИАТОР] -> [СООБЩЕНИЕ]`
*   *Пример:* `[10:15:32][CRITIQUE_REJECT][Architecture_Critic] -> Отклонил схему БД. Причина: Пароли пользователей планируется хранить в открытом виде, отсутствует поле salt/hash.`
*   *Пример:* `[10:17:11][ESCALATION][Developer] -> Откат на этап Архитектуры. Причина: Найдено логическое противоречие в связях таблиц Orders и Users.`

#### Поток Б: Системная телеметрия (Machine-Readable JSON Log)
Высокоточный технический лог для оценки производительности, стоимости системы и последующего Fine-Tuning моделей.
Каждая запись представляет собой JSON-объект следующей структуры:
```json
{
  "timestamp": "2026-10-27T19:15:32.001Z",
  "project_id": "prj_98432",
  "stage": "ARCHITECTURE",
  "agent_role": "Architecture_Critic",
  "llm_model": "claude-3-5-sonnet-2026",
  "metrics": {
    "prompt_tokens": 14205,
    "completion_tokens": 842,
    "execution_time_ms": 3120,
    "api_cost_usd": 0.051
  },
  "tool_calls": [],
  "status": "REJECT"
}
```

### 9. Управление Контекстом и Экономия Токенов (Context Optimization)
Для предотвращения деградации ответов LLM из-за перегрузки памяти и снижения финансовых затрат на API, оркестратор применяет три правила чистки контекста:

1.  **Сжатие истории при транзите (Stage Transit Pruning):** Когда этап `ARCHITECTURE` успешно завершен и Критик поставил `APPROVED`, вся многошаговая история споров, черновых вариантов схемы и промежуточных промтов полностью стирается из активной памяти. Следующему агенту (Разработчику) передается *только финальный, чистый артефакт* архитектуры.
2.  **Саммаризация при эскалации (Escalation Summarization):** При откате назад (например, из Тестирования в Разработку) оркестратор не пересылает Разработчику весь лог выполнения 50 тестов. Оркестратор вызывает легковесную модель для создания `Error Summary` (короткой выжимки: какие строки упали и почему), и передает Разработчику только этот сжатый отчет.
3.  **Дифференциальная память (Diff-only Context):** При работе с кодом Агент-Разработчик никогда не получает в контекст весь репозиторий. Используя инструмент поиска, он запрашивает структуру классов (AST-дерево) или конкретный метод, работая в рамках узкого, сфокусированного окна видимости.
