# Спецификация платформы Autonomous AI Software Engineer v1.0

## 1. Архитектурный манифест (Концепция)
Платформа является абстрактной средой выполнения задач миграции и рефакторинга кода. Архитектура построена на полном разделении управляющих алгоритмов (ядро), динамической бизнес-логики (изменяемые модули) и базы знаний (внешние промпты).

## Главное правило разработки:
Никакого естественного языка (промптов, инструкций, ТЗ) внутри Python-кода. Любые системные и пользовательские инструкции моделей должны храниться в каталоге `prompts/` в виде изолированных текстовых файлов.

## 2. Анатомия каталогов и зон доступа
Система строго разделена по уровням изменчивости (mutability). Агенту запрещено модифицировать файлы, находящиеся в контуре безопасности.

```text
ai-agent/
│
├── core.py                  # [IMMUTABLE] Неизменяемое микроядро («мозжечок»)
├── core_tools.py            # [IMMUTABLE] Системный контур API-инструментов (ls, cat, db)
├── initializer.py           # [MUTABLE / BY USER] Инициализатор планов миграции
├── agent.py                 # [MUTABLE / BY USER] Главный диспетчер (оркестратор конвейера)

├── migration_manifest.json  # [USER CONFIG] Вводные параметры ТЗ от человека
├── tasks.json               # [DYNAMIC REGISTRY] Текущий пошаговый реестр задач миграции
├── prompts.json             # [CONFIG] Реестр промптов (все ключи → file_path в prompts/)
├── prompts1.json            # [BACKUP] Резервная копия конфига промптов
│
├── modules/                 # [AUTONOMOUS EVOLUTION] Изменяемые программные компоненты
│   ├── parser.py            # Модуль извлечения Markdown-кода
```

## 3. Правила стабильности локального ИИ (Ollama Guardrails)
Для предотвращения галлюцинаций и сбоев локальных моделей (14B–30B), ядро и модули обязаны соблюдать три системных правила:

   1. **Изоляция исполнения (Subprocess Run)**: Любые тесты (unittest) и компиляция кода запускаются исключительно через `subprocess.run()`. Код возврата `returncode == 0` является единственным критерием успеха. Поиск строковых маркеров (вроде "SUCCESS") в stdout запрещён.
   2. **Текстовый протокол вместо JSON (ReAct Tool Calling)**: Локальные модели нестабильно работают с аппаратным `format="json"` при вызове инструментов. Вызов системных команд осуществляется строго через текстовые XML-подобные теги: `<call name="tool_name">args</call>`.
   3. **Извлечение кода из Markdown**: Модуль `modules/parser.py` извлекает блоки ` ```python ` из ответа модели через `re.search()`. Всегда оборачивай код в такой блок. Извлечённый код проходит `.strip()`.

## 4. Контур безопасности ядра (core.py)

Ядро является единственным мостом между ИИ и операционной системой:

- **Загрузка промптов**: `load_prompt()` и `load_prompt_from_file()` — читают промпт из `file_path` (файл `prompts/<ключ>.txt`) или из inline `prompt` в `prompts.json`, если `file_path` отсутствует.
- **Обновление промптов**: `update_prompt_file()` и `update_prompt_in_file()` — проверяют флаг `mutability` (immutable блокируется), затем пишут либо в файл на диск (есть `file_path`), либо в inline поле `prompts.json`.
- **Запуск тестов**: `run_isolated_tests()` — запускает `python test_*.py` через `subprocess.run()`. Критерий успеха — `returncode == 0`.
- **Горячая перезагрузка (Hot Reload)**: `hot_reload()` — выполняет `os.execv(sys.executable, [sys.executable] + sys.argv)`, полностью перезапуская процесс в памяти.
- **Модели Ollama**: `call_ollama()` — принимает опциональный `model_override`. По умолчанию `qwen2.5-coder:14b`, для SDD/архитектора — `qwen3-coder:30b`, для мета-оптимизации промптов — `deepseek-r1:32b`.

------------------------------
## 5. Протокол взаимодействия ролей (Цикл SDD → TDD → Coding → Critic)

Каждая задача из `tasks.json` обрабатывается универсальным исполнителем (`modules/executor.py`) строго по конвейеру:

```text
[Манифест] ➔ [Глобальный Архитектор] ➔ Создание плана (tasks.json)
                                               │
 ┌──────────────────────────────────────────────┘
 ▼
[SDD Фаза] ➔ Создание архитектурного ТЗ (модель 30B)
 │
 ▼
[TDD Фаза] ➔ Написание unit-тестов ДО кода (модель 14B)
 │
 ▼
[Кодинг Фаза] ➔ Написание целевого кода (модель 14B)
 │
 ├─► [Успех (returncode 0)] ➔ Статус задачи "completed"
 │
 └─► [Провал] ➔ [Фаза Критика] ➔ Авто-исправление кода (до 3 попыток)
                    │
                    └─► [Тупик] ➔ [Мета-Оптимизация Промптов]
                       → Анализ через deepseek-r1:32b
                       → Обновление prompts/<роль>.txt
                       → Горячая перезагрузка (hot_reload)
```

------------------------------
## 6. Реестр изменяемости промптов (prompts.json)

Все промпты хранятся на диске в `prompts/*.txt`. `prompts.json` содержит только метаданные: ключ, путь к файлу, описание и уровень мутабельности.

Уровень автономии агента при изменении собственной базы знаний жестко контролируется флагом `mutability`:

| Mutability | Что происходит при попытке изменения |
|---|---|
| `immutable` | Ядро блокирует операцию, выводя `[red]🚫 ... заблокирована ядром![/red]` |
| `user_approved` | Агент может предложить новый текст, ядро запрашивает y/n в терминале |
| `autonomous` | Полная свобода агента. Промпт перезаписывается без участия человека |

**API загрузки/обновления**:
- `load_prompt(role_key)` — читает из `file_path` (если есть) или inline `prompt` (обратно совместимо)
- `load_prompt_from_file(role_key)` — то же самое, явное именование
- `update_prompt_file(role_key, new_text)` — пишет в файл (есть `file_path`) или в inline поле JSON
- `update_prompt_in_file(role_key, new_text)` — пишет только в файл на диск

## 7. Зависимости

Только `requests` и `rich` (см. `requirements.txt`). Никаких дев-зависимостей (pytest, flake8, mypy и т.д.).

Тесты используют стандартный `unittest`, запускаются через `python test_*.py`.
